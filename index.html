Most machine learning courses end where the real work begins. You load data, engineer some features, train a model, print accuracy: 0.94, and the notebook ends. In industry, that notebook is roughly the first 5% of the job. The remaining 95% is everything required to make that model run reliably, repeatedly, and safely for months or years while the data underneath it keeps changing.

MLOps is the discipline that covers that other 95%. Every tool you'll eventually touch — an experiment tracker, a container, a CI pipeline, a model registry — is a tool that solves one specific MLOps problem. Learn the tools without the problems and you get a toolbox with no judgment. This reading builds the judgment first.

By the end of this reading, you can

Explain why ML systems fail in production for reasons that have nothing to do with model accuracy — describe the ML lifecycle and where it breaks — apply six core MLOps principles — place any project on a maturity scale and name its next gap — and take a training script from "trust me" to "verify me."

01 / Motivation

Why ML projects die after the notebook

This story isn't hypothetical. Some version of it happens at nearly every company that adopts ML.

A retail bank builds a fraud detection model. A data scientist spends six weeks on it in a notebook. Final numbers: 0.96 ROC-AUC on the held-out test set. Leadership is thrilled. The model is approved for production. Then reality arrives.

Read that log again and notice something important: not one of those failures is a modelling problem. The model was fine. The system around the model did not exist.

The bottleneck is almost never the algorithm — a widely cited industry observation is that most ML models never reach production, and of those that do, a large share silently degrade. It's engineering, process, and operations.

A machine learning model is not a deliverable. A machine learning system is the deliverable — the model is one component inside it, usually the smallest one.The core insight of this course

Hidden technical debt

In 2015, a team of Google engineers (Sculley et al., published at NeurIPS) argued that only a small fraction of the code in a real ML system is the ML code itself — the rest is infrastructure: data collection, feature extraction, verification, configuration, serving, monitoring, process management.

They coined a phrase worth memorizing: changing anything changes everything — the CACE principle. In ordinary software, you can change a module and reason about the blast radius. In an ML system, changing one input feature changes the learned weights of every other feature. There are no isolated changes.

Traditional software is Lego

Swap one brick and the rest of the structure holds. You can reason locally about a change.

A model is a knitted sweater

Pull one thread and the shape of the whole garment changes. This is why ML systems need stronger engineering discipline than ordinary software, not weaker.

The paper catalogues forms of ML-specific technical debt worth knowing by name:

Entanglement

Features aren't independent; touching one perturbs the whole model (CACE).

Correction cascades

A model built to patch another model's errors, then a third to patch the second. Nothing can be retrained independently.

Undeclared consumers

Teams silently consume your model's output; you can't change or retire it without breaking them.

Data dependency debt

Your model depends on an upstream table nobody owns, that someone can change without telling you.

Configuration debt

Dozens of hyperparameters, thresholds, and paths scattered across scripts with no single source of truth.

Pipeline jungles

Data prep built up as an organic pile of scripts no one can rerun end to end.

Dead experimental paths

if use_new_features_v2: branches never removed, silently affecting behavior.

02 / Definitions

What is MLOps?

MLOps is the set of practices, principles, and tooling for reliably building, deploying, and maintaining machine learning systems in production.

A more useful working definition for engineers: MLOps is what turns a model into a service — something with a version, an owner, a deployment process, a monitoring dashboard, a rollback plan, and a defined path for improvement.

MLOps sits at the intersection of three established disciplines. Each contributes something non-negotiable, and MLOps adds what none of them handle on their own: the model as a versioned, decaying, data-dependent artifact.

From software engineering

Version control, code review, testing, packaging, releases, rollbacks.

From DevOps

Automation, CI/CD, containerization, infrastructure as code, observability, on-call.

From data engineering

Reliable pipelines, schema contracts, data quality gates, lineage.

What MLOps is not

  • Not a tool. Not "MLflow" or "Kubeflow" or "SageMaker" — those are implementations. You can do good MLOps with a shell script and disciplined Git usage, and terrible MLOps with a million-dollar platform.
  • Not just deployment. Deployment is one stage. Monitoring, retraining, governance, and rollback are equally part of it.
  • Not only for large companies. A two-person team with one model benefits immediately from pinned dependencies, a seed, and a run log. Scale changes which practices pay off, not whether they matter.
  • Not a separate team's problem. In most organizations, the data scientist who trained the model is expected to understand how it ships and how it's monitored.
  • Not about perfection. It's about maturity levels — knowing where you are, and what the next improvement should be.
03 / Comparison

DevOps vs. MLOps: three axes of difference

If DevOps already solved software delivery, why a new discipline? DevOps solves most of it — but ML systems differ in three structural ways, and each difference forces new practices.

DevOpsMLOps
Versioned artifactsCodeCode + data + model + features + config + environment
"What produced this output?"The commit SHAThe commit SHA and the training data snapshot and the hyperparameters and the library versions

In DevOps, git log gives you the full story. In MLOps it gives you the screenplay but not which actors turned up that day: two engineers can run byte-identical code and get different models, because the data changed. This single fact is why data versioning and experiment tracking exist.

Traditional software is deterministic and specified: add(2, 2) must return 4. A unit test passes or fails — binary. An ML model is statistical and unspecified: there's no single correct output for a given input, only a distribution of acceptable behaviour.

  • You can't assert predict(x) == y. You assert roc_auc >= 0.93 on the holdout set.
  • New test types DevOps has no concept of: data validation (is the schema and distribution as expected?), model quality gates (does the candidate beat the incumbent?), behavioural tests (does the prediction move the right way as a key feature increases?), fairness checks (is performance uniform across segments?).
  • Passing tests never proves correctness — only that the model hasn't obviously regressed.

This is the most important difference, and the one that surprises people coming from software. Deployed code doesn't get worse on its own. A correctly functioning API endpoint deployed in January behaves identically in December if nothing changes. A deployed model does get worse on its own, because the world it learned from moves away from the world it now sees.

Code is a bridge

Built correctly, it still stands in December.

A model is a map

Printed correctly, still accurate — of a city that has since built three new roads and closed a fourth. Nothing in the map changed. That's precisely the problem.

Four mechanisms drive it: data drift (the input distribution shifts), concept drift (the input→output relationship itself shifts), upstream changes (a column silently changes from dollars to cents), and feedback loops (the model's own decisions shape the data it's later retrained on).

The four C's

The operational consequence: an ML system is never "done." It needs continuous monitoring and a defined retraining path — which is why MLOps extends CI/CD with two more C's.

CI

Continuous Integration

Test and build on every change; for ML this also means validating data and models.

CD

Continuous Delivery

Ship the validated artifact to an environment automatically once CI passes.

CT

Continuous Training

Retrain on fresh data automatically, on a schedule, drift alert, or new data volume.

CM

Continuous Monitoring

Watch data quality, prediction distributions, and business metrics — always on.

Making drift concrete

A logistic regression is trained on one quarter of fraud data — where fraud looks like large transactions at high velocity — and evaluated on a held-out slice of the same quarter. No code changes between here and the next quarter; only the world does.

Service health (DevOps)

Latency, throughput, error rate, CPU, memory. Tells you the system is alive.

Model health (MLOps)

Input distributions, prediction distributions, feature nulls, segment performance, business KPIs, and — once labels arrive — actual accuracy. Tells you the predictions are still worth trusting.

The asymmetry to remember

Input drift is an alert, not an incident — it says the model is operating outside validated conditions, which is a reason to look, not proof anything is broken. Data drift is detectable from inputs alone, in real time, without labels. Concept drift is the one that actually destroys performance — and detecting it generally needs labels, which arrive late or never. Much of practical monitoring design follows from that one trade-off.

4.1 / Worked example

What "better" looks like, in practice

The diagnosis is the drift demo above. Here is a first dose of treatment — roughly twenty extra lines over the naive version, moving the work from "trust me" to "verify me."

Stages 1–4, in one cell — exactly where most projects stop 
# Stage 1 — Data
df = load_breast_cancer(as_frame=True).frame

# Stage 2 — Features (already numeric here; in real projects this stage dominates)
X, y = df.drop(columns=["target"]), df["target"]

# Stage 3 — Train
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.2, stratify=y, random_state=42)
clf = RandomForestClassifier(n_estimators=200, max_depth=6, random_state=42).fit(X_tr, y_tr)

# Stage 4 — Evaluate
roc_auc_score(y_te, clf.predict_proba(X_te)[:, 1])  # 0.9940 — but can anyone else get this number?

# Stages 5, 6, 7 — deployment, monitoring, retraining — do not exist in this cell.
# That gap is the entire subject of this course.
Every knob, one place 
CONFIG = {
  "seed": 42,
  "test_size": 0.2,
  "n_estimators": 200,
  "max_depth": 6,
  "threshold": 0.5,
}
# + a sha256 hash of the exact
# training dataframe (16 chars)
# + captured library versions
# (numpy, pandas, scikit-learn,
# python) at training time
metadata.json — saved beside the model file{
  "model_type": "RandomForestClassifier",
  "data_hash": "a13f...92c0",
  "metrics": { "roc_auc": 0.994 },
  "environment": {
    "python": "3.11",
    "scikit_learn": "…"
  }
}

Same model, same metric, very different trustworthiness. Ask what you can now answer that you couldn't before: which exact rows trained this model (the data hash), can a colleague reproduce 0.994 on a laptop (config + environment), and which model is this, six months from now (the file travels with its metadata). When you later meet a tool like MLflow, notice it's doing exactly this — automatically, queryably, at scale. The concept will already be familiar; only the interface is new.

Five habits, twenty minutes

Hyperparameters in one config object, not scattered literals · one recorded seed used everywhere randomness enters · a content hash of the exact training data · library versions captured at training time · a metadata file written beside the model artifact. This is Level 0 done honestly — the floor for everything after.

05 / Framework

The six MLOps principles

Tools change every eighteen months. These principles don't. Learn them and you can evaluate any tool — including ones that don't exist yet — by asking which of these it helps you satisfy.

01Version everything, not just code⌄
StatementEvery input that can change the output must be versioned and referenceable: code, data, features, model artifacts, hyperparameters, environment, and configuration.
Failure it prevents"The model in production performs differently from the one I evaluated, and I can't determine why." Without versioning, this is unanswerable.
Minimum viable practiceGit for code. A content hash for every training dataset. A pinned requirements file. Hyperparameters in a config file. A metadata file saved next to every model artifact.
02Reproducibility is a hard requirement⌄
StatementAnyone on the team, on a different machine, must be able to reproduce a reported result from recorded information alone — no tribal knowledge.
Failure it preventsUnreproducible results are unverifiable results. You can't debug a regression, satisfy an auditor, or safely hand a project over.
Minimum viable practiceSet and record every random seed. Fix the data split deterministically. Pin library versions. Record the code commit alongside the metrics.
Seeds are necessary but not always sufficient — GPU kernels and non-deterministic library defaults can still shift results slightly. Aim for reproducible within a stated tolerance by default; treat bit-exact reproducibility as a stronger guarantee you engineer deliberately when required.
03Automate everything that will be done twice⌄
StatementManual steps are where errors live. If a process will run more than once, it should be a script; if it runs on an event, it should be a pipeline.
Failure it preventsThe 3 a.m. deploy where step 6 of an 11-step runbook is performed from memory, incorrectly. Also the quieter failure: a process so tedious that people avoid doing it, so retraining stops happening.
Minimum viable practiceOne command trains the model end to end. One command builds the deployable artifact. No sequence of notebook cells run in a specific undocumented order.
04Continuous training, because models decay⌄
StatementRetraining is a designed, scheduled, monitored part of the system — not an emergency response.
Failure it preventsSlow, silent degradation — a fraud model quietly falling from 89% to 61% catch rate over five weeks.
Minimum viable practiceWrite down the retraining trigger and cadence before you deploy. "We retrain monthly against a fixed holdout" is a policy; "we'll retrain when someone notices" is not.
05Monitor the model, not just the server⌄
StatementInstrument data quality, input distributions, prediction distributions, segment performance, and business KPIs — and alert a named owner when they move.
Failure it preventsGreen dashboards and a broken product — the most dangerous state in ML operations, because nobody is looking for the problem.
Minimum viable practiceLog every prediction with its inputs, a model version, and a timestamp. You can't investigate what you didn't record.
06Governance, collaboration, reviewability⌄
StatementML systems are cross-functional. Ownership, documentation, approval paths, and access control must be explicit.
Failure it preventsThe bus factor of one. The unauditable model. The credential committed to a public repository.
Minimum viable practiceA named owner per model. A model card describing intended use, training data, metrics, limitations, and known failure modes. Code review on ML code, including pipeline config. Secrets in a secret store, never in a repo.
When you meet a new tool, ask: which principle does this serve, and what did people do before it existed? That question turns tool-learning into engineering judgment.
06 / Self-assessment

MLOps maturity: knowing where you are

You don't implement MLOps all at once — you move up levels. The most widely used framing (from Google's MLOps whitepaper) has three levels, and placing a project on this scale is a genuinely useful professional skill.

  • Data prep, training, and evaluation happen interactively in notebooks
  • Handoff to deployment is a file and a conversation
  • Deployment is manual and infrequent — quarterly or on request
  • No CI/CD for the ML code; no monitoring of model quality
  • Retraining happens rarely, usually after someone complains

This is where nearly every ML course leaves you, and where a surprising number of real companies still are. Not shameful — a legitimate starting point for a first model. It becomes dangerous once the model starts making real decisions.

  • Modular, tested components; one command or trigger runs the whole training flow
  • Experiments are tracked; data and models are versioned
  • Automated data and model validation gates
  • Continuous training is possible — retraining triggered by schedule or drift
  • Deployment of the model is automated, even if pipeline code still ships manually
  • Often a feature store to guarantee train/serve consistency

Most production teams live here, and that's often the right economic choice.

  • Source changes trigger build, test, and deployment of the pipeline components themselves
  • Multiple environments (dev → staging → prod) with progressive rollout
  • Automated model promotion through a registry with approval gates
  • Comprehensive monitoring feeding automated retraining
  • Rollback is a tested, one-command operation

Pays for itself with many models, frequent retraining, or regulatory pressure. Deciding not to climb further, for stated reasons, is a legitimate engineering decision. Not knowing which level you're on is not.

Checkpoint — place your own work on the scale

Take a project you have actually built — a course project, an internship task, a Kaggle pipeline — and answer these twelve questions honestly. Each one is a yes or a no.

  1. Can someone else reproduce your headline metric from your repository alone?
  2. Is the exact training dataset for your best model recoverable today?
  3. Are all hyperparameters in a config file rather than scattered as literals?
  4. Does one command run data prep → train → evaluate, end to end?
  5. Is every experiment's parameters and metrics recorded automatically?
  6. Are dependencies pinned, so the environment is rebuildable?
  7. Is there an automated gate that would block a bad model from deploying?
  8. Is deployment automated and repeatable, with no manual runbook?
  9. Would you detect input drift within a day of it starting?
  10. Is there a written — and tested — rollback procedure?
  11. Does the model have a named owner and a model card?
  12. Is retraining triggered by policy rather than by a complaint?

Scoring: 0–3 is Level 0. 4–8 is a partial Level 1, automating with real gaps. 9–10 is a solid Level 1. 11–12 is Level 2.

Then write down three things: your level, the lowest-numbered question you answered no to, and the concrete action that would close that gap this week.

The rule for what comes next

Fix the lowest-numbered gap first. Maturity is climbed in order, not cherry-picked — automated deployment on top of an unreproducible pipeline just ships your irreproducibility faster.

07 / People

Roles: who does what

MLOps is cross-functional, and a recurring source of production failure is an unclear boundary between these roles.

RoleOwnsTypical artifacts
Data EngineerReliable data availability and qualityPipelines, warehouse tables, schema contracts
Data ScientistProblem framing, features, model qualityExperiments, evaluation reports, trained candidates
ML EngineerProduction-grade ML code and servingTraining pipelines, model services, feature transforms
MLOps / Platform EngineerThe infrastructure everyone else builds onCI/CD, containers, registries, monitoring, IaC
Software EngineerThe application consuming predictionsAPI integrations, product surfaces
Product / Domain OwnerBusiness metric, cost asymmetry, acceptanceCharter, success criteria, launch approval
Risk / ComplianceFairness, explainability, auditabilityModel cards, audit trails, approvals

In small teams, one person wears three or four of these hats — the most common situation, and exactly why understanding all of them matters even if your title is "Data Scientist." The Data Scientist / ML Engineer boundary is the most contested one in the market: job titles are inconsistent, so read the responsibilities, not the title.

Bolded tools form the most common commercial configuration in industry — a Git-based workflow, open-source experiment tracking, containers, and a major cloud's managed ML platform. The specific tools matter far less than the pattern: skills transfer, and the concepts transfer completely.

Does this apply to foundation models?

A fair question, since a growing share of production "ML" is now an API call to a model you didn't train. Short answer: the lifecycle survives almost entirely intact — the stages change contents, not their existence. Business framing, evaluation gates, deployment patterns, monitoring, versioning, rollback, governance, and a named owner all stay the same. Every one of the six principles applies unchanged.

StageClassical MLFoundation models
DataTraining datasetRetrieval corpus, its chunking and embedding strategy, refresh cadence
FeaturesTransformationsPrompt templates and context assembly — versioned exactly like code, because they are code
TrainingFit a modelPrompt iteration, retrieval tuning, occasionally fine-tuning
EvaluationHeld-out metricsCurated eval sets, LLM-as-judge, human review — non-determinism means evaluating distributions of outputs, not single answers
DeploymentYour containerOften a vendor endpoint: latency, rate limits, and token cost become first-class constraints
MonitoringDrift in featuresDrift in user inputs, plus output quality, refusal rates, hallucination and safety incidents, cost per request
One genuinely new failure mode

The model can change underneath you. A vendor updates a model behind the same API name, and carefully tuned prompts silently behave differently. In classical ML the artifact is frozen and the data moves; here, both can move. Pin model versions explicitly where the vendor allows it, and keep a regression eval set you can re-run on demand.

09 / Field notes

Common pitfalls, and how to avoid them

The mistakes that show up repeatedly, from students and professionals alike. Each is cheap to avoid and expensive to fix later.

1

Optimizing the model when the bottleneck is the system

Three weeks of hyperparameter tuning for +0.4% AUC, on a model that takes six weeks to deploy and has no monitoring. Fix the system; marginal model gains are usually the least valuable work available.

2

Treating the notebook as the deliverable

Notebooks are excellent for exploration and terrible as production artifacts — hidden state, out-of-order execution, no testability, unreviewable diffs. Explore in a notebook; ship a module.

3

Skipping reproducibility because "it's just an experiment"

Every experiment is "just an experiment" until it becomes the model everyone depends on. Seeds and config files cost two minutes.

4

No data validation

Your model will happily consume garbage and return confident nonsense. A schema and range check at the pipeline entrance catches most real incidents.

5

Deploying without a rollback plan

And more common: having a plan you've never executed. Rehearse it once while nothing is on fire.

6

Broad, convenient credentials

"Let's just use admin permissions for now." Later never arrives; the credential ends up in a public repo. Least privilege from day one.

7

Overly broad, unactionable monitoring

An alert that fires daily is not an alert; it's noise, and people build filters to hide it. Alert on things a named human would actually act on.

8

Building for scale you don't have

Kubernetes, a feature store, and a streaming pipeline for one model scoring 400 rows a day. Batch scoring on a schedule is a perfectly respectable production architecture.

9

No named owner

Models without owners don't get monitored, retrained, or retired. They quietly rot in production.

10

Learning tools instead of principles

The five-year half-life of MLOps tooling is real. The six principles have outlived several complete generations of tools.

10 / Synthesis

Class summary

The problem

ML projects fail in production for engineering and operational reasons, not modelling ones. Non-reproducible results, unversioned data, training/serving skew, undetected drift, impossible rollbacks — none of these are solved by a better model.

The discipline

MLOps applies software engineering, DevOps, and data engineering practice to ML systems, and adds what those disciplines never had to handle: a model as a versioned, data-dependent, decaying artifact.

Three differences from DevOps

You version more than code; "correct" is statistical rather than specified, so testing becomes gates and validation; deployed models degrade on their own — which is why CI/CD becomes CI/CD/CT/CM.

Maturity

Level 0 (manual) → Level 1 (automated training pipeline) → Level 2 (CI/CD-automated platform). Know your level; fix the lowest gap next.

business framing → data → features → experimentation → evaluation → deployment → monitoring → retrain → (back to data)

The six principles, once more: Version everything · Reproducibility · Automation · Continuous training · Monitor the model, not just the server · Governance and collaboration.

Reference

Glossary

Terms used throughout this reading. Skim now, or search when one shows up unexplained.

Artifact
Any versioned output of a stage that a later stage consumes — a dataset snapshot, a trained model file, a container image, an evaluation report.
Model registry
A catalogue of trained models with versions, stage labels (staging/production/archived), lineage, and approval status.
Quality gate
An automated pass/fail check in a pipeline; a model or dataset that fails does not proceed — no case-by-case override.
Lineage
The recorded chain from raw source to deployed model: which data, which code commit, which parameters, which run.
Training/serving skew
Any difference between how a feature is computed during training and during serving. The most common production ML bug.
Data drift / covariate shift
The input distribution P(X) moves away from what the model was trained on. Detectable without labels.
Concept drift
The relationship P(y|X) itself changes. Usually requires labels to detect — the one that actually destroys performance.
Incumbent (champion)
The model currently in production, and the baseline any candidate must beat.
Challenger
A candidate model being evaluated against the incumbent before promotion.
Shadow deployment
Serving live traffic to a new model while discarding its predictions, purely to compare at zero risk.
Canary
Routing a small slice of real traffic (say 5%) to a new model, watching, then ramping up or rolling back.
Blue/green
Two complete environments; traffic is flipped from one to the other and can be flipped back instantly.
Feature store
A system that stores feature definitions and values so the same definition serves both training and inference.
Model card
A short document shipping with a model: intended use, training data, metrics, limitations, known failure modes, owner.
CT / CM
Continuous Training and Continuous Monitoring — the ML-specific extensions to CI/CD.
